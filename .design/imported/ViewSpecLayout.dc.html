View standards

These rules apply to each side view: Schema, Connections, Git, Files, History, and Snippets. Each view uses the same parts in the same order. Each part has the same size in each view. The Schema view is the reference.

  1. Header row. The view title, then the scope (connection › database, workspace, or branch). The scope opens a menu that changes the scope. On the right: one primary action as an icon button, then the overflow menu (⋯). Each other action goes into the overflow menu and into the context menu.
  2. Toolbar. The filter field comes first and fills the width. A filter menu can follow it. A view with more than one mode (Git: Changes · History · Branches) shows a tab row between the header and the toolbar. The filter applies to the current mode. Do not show a mode that does not exist yet.
  3. Body. One tree or one list. Rows have one height. Group headers divide a list (by day, by environment, by state). The body is the only part that scrolls.
  4. Status line. Optional. It shows the count and the age of the data, or a pending operation. It never shows an error: an error goes to the top of the body.
  5. Selection. A selected row has a filled background. The text weight does not change, so the row does not move. A focused row also has a 2 px focus ring.
  6. Detail. The detail of the selected row opens as a preview tab in the editor area (see the layout below). It does not open in a modal dialog or in a panel on top of the view.

Why a preview tab and not a panel that slides in

The side view is 220 to 480 px wide. A detail panel in it covers the tree, or it makes the tree too narrow. The editor area has the width for the columns of a table and for a diff. The tab gives the keys that you know (Ctrl+Tab, Ctrl+W) and a back history. Today the app already shows a table and a diff as tabs.

A preview tab has an italic title. A single click or Space shows the detail and keeps the focus in the view. Enter shows the detail, keeps the tab, and moves the focus into it.

  • Use monospace for code only: types, SQL, default values, index definitions, commit hashes, cell values.
  • Object names (tables, columns, collections, files, branches) use the UI font in all places. They are labels.
  • Do not use bold to show the selection. Use the selection background.
  • Do not use capital letters for headers. Use sentence case.
  • Cut long text at the end with an ellipsis. The tooltip shows the full text. For a path, cut the start: …/reports/runs_by_day.sql.

4. Status

One scale for all views. Each state has a colour and a shape. The shape stays the same in each theme, so a person who does not see the colour can see the state.

  • Put the status mark before the label. Put the status text after the label, or in the tooltip.
  • The environment badge (Development, Staging, Production) is not a status. It is a pill with text. Its colours stay as they are today.
  • The accent colour (#b45309) marks the active tool and AI actions only. It does not mark a status.
  • Neon and High contrast colours: see part 3, Colour themes.

5. Icons

One set: stroke icons on a 24 grid, stroke 1.75, round ends. Size 16 in rows and buttons, 18 in the tool strip. Colour: muted text colour. The active tool and AI actions use the accent colour.

  • One icon has one meaning in all views. Do not use the table icon for a file.
  • An icon-only button has an accessible name and a tooltip. The tooltip shows the shortcut: "Read the schema again (F5)".
